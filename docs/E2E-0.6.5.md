# 0.6.5 E2E findings (2026-09-13)

## Run A — local mode via the live dashboard (devloop-trial)
- A-1 (Low) Trunk taken from origin/HEAD without .pilot.yml: a repo cloned from a local checkout whose HEAD was a feature branch showed trunk "devloop/subtract" and "ahead/behind trunk 0/2". main/master stay protected regardless. Real GitHub clones set origin/HEAD=main, so rarely hit; could prefer main/master when they exist, or say where the trunk came from.
- A-2 (Low) The task's commit on the work branch is titled "devloop: delegate" — no task id or title. In a real repository's history every DevLoop commit reads the same; `git log` cannot say which task made which change. Use "<taskId>: <title>" (and the review verdict/reviewer in the body).
- A-3 (Low) `.devloop/` stays untracked (`?? .devloop/` in git status) in the user's repository after a run. Readiness ignores it, but in an in-progress repo it is noise and one `git add -A` away from committing STATE/EVENTS. Add it to `.git/info/exclude` when the loop starts (never touch .gitignore), or say so in the start checks.
- A-4 (Medium, found reading the code during B) Worktree creation runs `git worktree add -B devloop/<taskId>`: an existing local branch of that name is reset to the base without asking. In an in-progress repo a planner-chosen id like TASK-001 can collide with an old branch (the sandbox had a stale devloop/TASK-001); if that branch held unmerged work it would be lost (reflog only). Refuse, or pick a fresh name, when the branch exists and is not an ancestor of the base.
- A run itself: GOAL written from the page → codex planned 1 task (est. 35 lines/2 files; actual 25/2) → dsh flash implemented → prePrCheck passed (rules 1.2.2) → claude opus reviewed PASS with a precise report → merged into trial/work → goal_complete in ~80 s. npm test 5/5.
- A-5 (High for the intended use: one ongoing repo, goal after goal) After a goal completes, the page offers no way to start the next goal on the same repository: the start panel is gone, GOAL.md is create-only ("edit it by hand"), and STATE stays goalCompleted. The page says "Add new work as a new project", but the same root cannot be two projects. Workaround used here: on the machine, `mv .devloop ../<repo>-goal1.devloop`, then the page shows the start panel again and a second goal ran. Fix: a "Start a new goal" action on a completed project that archives .devloop/{GOAL,STATE,EVENTS,PLAN,REVIEW,PROGRESS,PR-LOG} under .devloop/archive/<ts>/ and re-arms, keeping budget history.
- A-6 (Low) Repository status compares with the local trunk: after the forge side moved main, a stale local `main` made "Ahead / behind trunk" read 3/0. Compare with origin/<trunk> when it exists, or say which ref.

## Run B — forge mode, sandbox (e2e/065, requireChecks on, local claude review first)
- B-0 Stale branch reuse: the planner again named the task TASK-001; local devloop/TASK-001 (old, merged) was reset by `worktree add -B` and the remote one fast-forwarded. Harmless here only because the old branch was already merged (see A-4).
- B-1 (Low) The task PR body says how to decide but not what was asked: no acceptance criteria, allowed paths, or the local reviewer's verdict/notes. The GitHub reviewer judges from the title alone. Include the contract (acceptance, allowedPaths) and "passed local review by claude/opus" with its notes, collapsed.
- A-7 Hold/resume from the page works: switched the checkout to main mid-review → held merge_onto_trunk before merging (main untouched) → the gate explained it → switched back → "Resume loop" (confirm text shown) → merged on the next tick, attempts still 1. Second and third goals ran after archiving .devloop by hand.

## Blocking the user's plan (forge by default, one ongoing repo)
- C-1 (High) forge settings are profile-wide: every project loop gets `{ ...config, root }`, so `forge.pushUrl` (and reviewers/base) name ONE GitHub repository for every project on the dashboard. Forge mode cannot be the default for more than one repository. Needs per-project forge settings, taken at registration (the page shows the origin URL read without insteadOf rewriting, the operator confirms it) and stored in the registry, never re-read from the workspace later.
- C-2 (High) = A-5: continuous goals on one repository.
- B-2 (Medium) After a forge merge the task's worktree is left in place (.devloop/worktrees/TASK-001 on devloop/TASK-001), so the branch cleanup fails every time: "cannot delete branch 'devloop/TASK-001' used by worktree". Local mode removes the worktree first; the forge path does not. Worktrees and branches pile up one per task, and the next goal reusing the same id meets it.
- B-3 (flow OK) PR #4: local claude review passed → PR opened into e2e/065 with the devloop label → CI green (requireChecks on) → clestons APPROVE at b8b377b → DevLoop re-read verdict+checks and merged on GitHub (6d11dcf) → checkout fast-forwarded → task done. Review wait ~17 min (PR-daemon's queue).
- B-4 (Low) The release body lists each task's head and branch but not its pull request number/link (#4); the reviewer has to look it up to check "approved at the head it merged with". Record each task's PR number when it merges and link it.
- B-5 Release PR #5 (e2e/065 → main) opened one tick after goal_complete, with the 0.6.5 decision line and the devloop label.
- B-6 Release PR #5 APPROVED by clestons at 6d11dcf → DevLoop merged it on GitHub (main 389c0cf). Full forge chain ran: task PR → local review → GitHub review → merge into work branch → release PR → review → merge to main. ~22 min, mostly review queue.

## From the LoopX study (hazards for "next goal", same repo)
- D-1 (High, latent) releaseOf(…, orMerged) falls back to ANY merged PR from the work branch: goal 2 on the same work branch would find goal 1's merged release and record goal 2 as released. Match state.release.number exactly.
- D-2 (High, latent) Task ids restart each plan (TASK-001…), so goal 2's branches collide with goal 1's devloop/<id> locally (worktree -B reset, A-4) and on the forge (non-force push refused if not an ancestor). Prefix ids per goal.
- D-3 (Medium, latent) usage maps keyed by task id: a new TASK-001 inherits the old attempt/review counters.
- LoopX model: a goal is long-lived; work units are todos; "done" is derived standby, not a latch; new work wakes it. Finished work stays with the goal (archive section + runs index).
