# `/goal` 交付契约模板

`run` 起跑时把下面整段给用户执行。占位符 `<>` 按本仓库实际填好再给，别原样丢出去。

---

## 标准版（照抄这段）

```
/goal 按 docs/agent/ 的规划把 <M1/全部> 交付完成。停止条件全部满足才算完成：tasks.md 无 READY task、无未合并的 open PR、followups 无 OPEN 项。

【怎么用文档】每开一个 task 前先读 tasks.md 拿到它的开发范围与验收命令；实现严格对照 architecture.md 的边界和 spec.md 的数据模型/状态机，不自由发挥；拿不准算不算做好了就查 acceptance.md。范围只做当前 task，不顺手改别的。

【怎么验证】按 tasks.md 里该 task 的验收命令逐条跑通，再跑 lint→typecheck→build→测试，全绿才提 PR。跑不过就修到过，不许标 DONE。开 PR 前必须做一次对抗式自审（找 race/安全/错误处理/边界/生产失败）。

【怎么等评审】PR 由外部评审服务裁决，不是我自己评，也不许自己 --admin 合并。按契约约 20 分钟内出结果。开完 PR 用 Monitor 跑 `pr-monitor.sh --pr <n> --wait-for-verdict`(它在没有新鲜裁决前保持静默),**并设 30 分钟硬上限**;只有评审 commit == 当前 head 才算裁决,到点仍没有就按 review-contract.md 的超时路径如实汇报后回主循环,不许瞎改也不许干等。拿到 APPROVED 就合并进 <集成分支> 并 safe-cleanup；拿到 CHANGES_REQUESTED 就先中立 triage（该改的改、不该改的回评论讲清业务理由、不阻塞的记进 followups），修完推上去触发再评审。

【等待期间做什么】等回执不算停工：回主循环挑下一个 READY task 继续开工，不要空转干等。

【什么时候可以停】只有三条停止条件全满足才报交付；确实需要我拍板产品方向/验收/架构时，把该 task 标 BLOCKED 记进 progress.md，先把不受影响的 task 全做完，最后带着问题清单一次问我。除此之外不许中途收工。
```

---

## 变体

**只做一个里程碑**：把首句改成 `把 M2 交付完成`，停止条件加一句 `（只统计 M2 下的 task）`。

**先跑通一个 task 试水**：`/goal 把 T1.1.1 做完并合并进 <集成分支>`，其余段落照抄。

**用户已有明确目标**：用用户的话当首句，后面四段【】照抄——那几段是操作契约，跟目标是什么无关。

**收工**：`/goal clear`。

---

## 为什么要这么写

- **不写「怎么用文档」** → 模型会凭印象实现，plan 白做。
- **不写「怎么验证」** → 会把「我觉得没问题」当验收，标 DONE 却没跑过验收命令。
- **不写「怎么等评审」** → 要么自己给自己 approve、要么 PENDING 时瞎改、要么干等空转。
- **不写「等待期间做什么」** → 一个 PR 卡住，整条线停摆。
- **不写「什么时候可以停」** → 「PR 开了在等 review」会被当成交付完成。
