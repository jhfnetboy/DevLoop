# 评审回执的中立三角判断（review triage）

**为什么需要这一步。** 评审你 PR 的是**外部服务**——它按设计只看这个 PR 的 diff/代码，
**没有本仓库的业务上下文**（roadmap、领域约束、为什么这样设计、上游保证了什么）。
而**当前仓库的会话有这些背景**。所以拿到评审回执后，**不能盲从、也不能盲拒**，
要以「更大的业务领域」为坐标，中立地裁决每一条意见。

要同时避免两个极端：

- **过度顺从 / 盲改**：因为被 flag 了就改，哪怕业务上下文说这本来就是对的 → 制造无谓改动，
  甚至推翻了一个有意为之的业务决策。
- **过度防御**：为了护自己的代码，反射性地否定有效批评 → 真 bug 被你辩护掉了。

还有一个中间陷阱——**钻牛角尖**：一条微观正确性意见（"这里理论上可能为 null"），
放到整个业务流程里看可能根本不成立、甚至是错的。**要在大领域里判断，别只盯着孤立的 diff。**

## 判断步骤

1. **先装业务上下文**：读本仓库 `CLAUDE.md`、`docs/agent/{roadmap,spec,architecture}.md`、相关领域文档。
   评审进程没有这些——这正是你的信息优势。
2. **逐条给每个 comment / finding 分四类**：

   | 类 | 含义 | 动作 |
   |:---|:---|:---|
   | **A. 有效且该修** | 结合业务上下文确实对、且阻塞 | 修 |
   | **B. 有效但不重要** | 真问题但不阻塞（小优化/边角） | 建**跟进 task**，不阻塞合并 |
   | **C. 上下文缺失/判错** | 评审缺业务背景，代码其实对（上游有保证/是有意的业务决策） | **不改**，在 PR 上回一条讲清业务理由 |
   | **D. 过激/过度防御式 nitpick** | 风格化、"理论上可能"、投机性 | 只在**trivial** 时顺手改，否则标注为非阻塞 |

3. **中立护栏**（每条都自检）：
   - 不因为「被指出了」就改（避免 cargo-cult 修改）。
   - 不因为「想护代码」就拒（有效批评就认，尤其安全/竞态/数据丢失这类）。
   - 不钻小领域牛角尖——一个微观正确性点，在完整业务流程下可能 moot 甚至反了。
   - 拿不准某条是不是「缺业务上下文」时，**倾向于回一条澄清、而不是默默照改或默默忽略**。

4. **决定动作后，务必在 PR 上留痕**：无论修、反馈、还是延后，都在 PR 上回一句（`gh pr comment <n>`），
   写清判断依据。原因有二：① 让下一轮评审看到你的理由（这是对话，不是单方面服从/拒绝）；
   ② 让人类和未来的自己看得懂当时为什么这么定。

## 反例（什么不该做）

- **盲改**：评审说「加个 null 检查」，但业务流程保证上游一定非 null → 加检查是噪音；
  应回复说明这个不变量，而不是照加。
- **过度防御**：评审发现一个真实竞态，你以「一直没出事」搪塞过去 → 这是防御，该修。
- **钻牛角尖**：评审挑一个一次性脚本里的变量命名 → trivial，顺手改或忽略，别开辩论。
- **只盯小领域**：评审说「这个函数没处理空数组」，但调用方业务上只会传非空（有 schema 约束）→
  属于 C 类，回复讲清约束，别为不可能的输入加防御代码。

## 与外部评审的关系（记住定位）

外部评审**故意**不带业务上下文地独立进行——这是它中立的来源，是好事。
**你作为本仓库会话，是叠在它之上的「业务上下文仲裁者」。**
反驳要作为 PR 回复贴出去（`gh pr comment`），让下一轮评审和人类都看得到你的推理。
既不盲从，也不盲拒——用业务大图去裁决每一条。

> 这套 triage 对 `decision=CHANGES_REQUESTED`（逐条过）和 `decision=APPROVED` 带 comment（合并前快速过一遍，
> 决定哪些转跟进 task）都适用。见 `phases/run.md` §1。
